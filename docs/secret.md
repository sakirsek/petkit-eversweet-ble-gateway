# Getting your fountain's auth secret

Everything in this project needs one value you do not have yet: your fountain's
**6-byte auth secret**. This page explains what it is, why it is unavoidable,
and the ways to get it — most reliable first.

Short version, if you are on Android and impatient:

```
# 1. Open the PetKit app, let it connect to your fountain, wait ~10 seconds.
# 2. Plug the phone into your computer with USB debugging on.
python tools/get_secret.py
```

That writes the secret straight into `config.json` without printing it.

---

## Why a secret is needed

The fountain answers exactly two commands to an unauthenticated peer:

- `CMD 213` — returns the deviceId and serial number
- `CMD 86` — verifies a secret

Every other command (state, history, settings) causes an **immediate
disconnect** until `CMD 86` has been answered with `01`. There is no pairing, no
bonding, no PIN — the secret is the whole access-control story.

The secret is **generated by PetKit's servers per device**, not derived from the
MAC, serial or deviceId. Several derivations were tried and every one was
rejected with `00`. So there is nothing to compute; it has to be recovered from
somewhere that already knows it.

It is 6 bytes (12 hex characters). `CMD 86` wants 8 bytes, with the two extra
zero bytes at the **front**, so a secret of `1a2b3c4d5e6f` goes on the wire as
`00001a2b3c4d5e6f`. Configs in this project store the plain 6-byte form.

> **Never send `CMD 73`.** It permanently rewrites the deviceId and secret on the
> fountain and can lock the official app out of your own device. Only a physical
> factory reset undoes it. This project never sends it, and neither should
> anything you build.

## Method 1 — the app's own log files (recommended)

**The PetKit Android app writes the secret to disk in plain text.** When it
connects to a fountain it logs a line containing `securityCheckAndSyncData
secret:...` into:

```
/sdcard/Android/data/<package>/cache/logs/YYYY-MM-DD.log
```

where `<package>` is `com.petkit.oversea` for the international app.

The useful part: on modern Android that directory is off limits to other apps
and to file managers, but **`adb` can still read it, without root.**

### With the script

```
python tools/get_secret.py
```

It finds the phone, locates the app, scans the logs newest-first, extracts the
secret and the fountain's MAC, and writes both into `config.json`. The secret is
not printed unless you pass `--show`.

### By hand

```
adb shell ls /sdcard/Android/data/com.petkit.oversea/cache/logs/
adb exec-out cat /sdcard/Android/data/com.petkit.oversea/cache/logs/2026-08-23.log | grep -i secret
```

Take the 12 hex characters after `secret:` and put them in `config.json` as
`"secret"`.

**If it says adb was not found:** it very often is installed but not on `PATH` —
Android Studio puts it in `~/AppData/Local/Android/Sdk/platform-tools` on
Windows, `~/Library/Android/sdk/platform-tools` on macOS. The script looks in
those places by itself; if yours is somewhere unusual, pass
`--adb /path/to/adb`.

### If it finds nothing

- **Open the app and actually connect to the fountain first.** The line is only
  written during a connection. Then re-run.
- Check today's file exists — the app rotates logs by date.
- Try `--all-logs` to scan older files too.
- Some app versions may stop logging this. If yours does, the fallbacks below
  are all that is left.

### How well is this tested?

**End to end, on real hardware.** On a OnePlus CPH2655 running Android 16 with
`com.petkit.oversea`, the script found adb outside `PATH`, found the phone,
identified the app, scanned that day's log, and recovered both the secret and
the fountain's MAC. The secret it produced was compared against the one the
gateway had been authenticating with for days: **identical.**

Its behaviour when things are missing was checked separately on a Xiaomi MI 8
(Android 15) with no PetKit app installed — it reports that clearly instead of
failing in a confusing way.

What is still unknown is how far this generalises: two phones, two vendors, two
Android versions, one app build. The log path and the log line could change in
a future app release.

If it works or fails for you, please say so in an issue. That is the single most
useful report this project can receive right now — and if it fails, the manual
`adb exec-out cat ... | grep -i secret` above is the ground truth to compare
against.

## Method 2 — read it out of the APK (how it was originally found)

This is how the protocol was worked out, not something you should need. Pulling
the APK with `adb shell pm path` + `adb pull` gives an unobfuscated app; the
relevant class is `...petkitBleDevice/ble/mode/CTW3DataConvertor`, and the
forward-padding rule is `ByteUtil.makeUpBtyesForward(b, 8)`.

Useful if you want to verify the protocol yourself, or if you have a different
fountain model and need to find its equivalent.

---

## Method 3 — Bluetooth HCI snoop log (unreliable)

In principle you enable `bluetooth_btsnoop_log_mode=full` in developer options,
restart Bluetooth, connect with the app, and read the `CMD 86` write out of the
capture.

In practice this failed on the one phone it was tried on: the vendor strips
snoop data out of bug reports, and the resulting `.cfa` was an empty 16-byte
file. Your mileage will vary by manufacturer. Treat this as a last resort, not
a documented path.

---

## Method 4 — PetKit's cloud API (unverified)

The secret is server-generated, so PetKit's own API plausibly exposes it to an
authenticated account, which would make all of the above unnecessary — log in,
fetch the device list, done. Projects like `petkitaio` already talk to that API
for other purposes.

**Nobody has checked whether the BLE secret is actually in those responses.**
It is listed here as a lead, not a method. If you confirm it either way, an
issue would be genuinely valuable — it is the difference between "needs adb and
Android" and "works for everyone".

---

## iOS users

There is no known way to do this on iOS. The app sandbox is not readable the way
Android's is, and no equivalent has been found.

If you have a Mac and an Android device you can borrow, use the Android route
once — the secret belongs to the fountain, not to the phone, so you only need to
extract it a single time and it keeps working afterwards.

---

## Keeping it safe

The secret is not a catastrophic credential — it grants BLE access to a water
fountain, and only to someone within radio range of your home. But:

- **Do not paste it into issues, screenshots, or chat.** It identifies your
  specific device.
- `config.json` and `esp32/main/secrets.h` are both gitignored. Keep it that
  way; check before you commit.
- If you fork this repo, re-check that no template file has picked up a real
  value. That has happened here before.

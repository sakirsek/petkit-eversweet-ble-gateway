# PetKit Eversweet Max 2 UVC (CTW3UV) BLE protocol

Everything here was measured against a real fountain, not inferred from the app
alone. Where something is a guess, it says so.

**Scope.** One device: advertising name `Petkit_CTW3UV_100`, model CTW3, a Telink
TLSR8258. Other PetKit fountains use different frames. The W5/CTW3 family is
related but not identical, and none of this is guaranteed to transfer.

**Prior art.** [`slespersen/PetkitW5BLEMQTT`](https://github.com/slespersen/PetkitW5BLEMQTT)
and [`aavdberg/ha-petkit`](https://github.com/aavdberg/ha-petkit) already cover
parts of this family. What this document adds that they do not appear to
document: the **drinking-history stream** (`CMD 212` / `CMD 80` / `CMD 68`), the
fact that it can be read **without consuming the records**, the full 42-byte
state map including the proximity sensor, and the app's visit-merging rule.

---

## Transport

No pairing, no bonding, no encryption. MTU negotiates to 158.

| | UUID | Direction |
|---|---|---|
| Service | `0000aaa0-0000-1000-8000-00805f9b34fb` | |
| TX | `0000aaa2-...` | client → fountain, write / write-no-response |
| RX | `0000aaa1-...` | fountain → client, notify |

### Frame format

```
FA FC FD | cmd(1) | type(1) | seq(1) | len(LE16) | payload | FB
```

`type` is `1` for a request and `2` for a reply. `seq` echoes back.

**A request with an empty payload gets no reply on this model.** Send a 2-byte
`00 00` placeholder instead. This costs hours if you do not know it: the device
simply stays silent and looks broken.

Example, `CMD 213` with a 2-byte zero payload, seq 0:

```
fa fc fd d5 01 00 02 00 00 00 fb
```

## Authentication

Before authenticating, the fountain answers exactly two commands:

- **`CMD 213`**: returns deviceId and serial number
- **`CMD 86`**: verifies a secret; replies `01` accepted, `00` rejected

Anything else (`200`, `210`, `211`, `66`, …) causes an immediate disconnect.

The secret is **6 bytes, generated by PetKit's servers per device.** It is not
derived from the MAC, serial or deviceId. Several derivations were tried and
all were rejected. `CMD 86` expects 8 bytes with the secret **forward-padded**,
i.e. two zero bytes at the front:

```
secret 1a2b3c4d5e6f  ->  payload 00 00 1a 2b 3c 4d 5e 6f
```

If `CMD 213` returns a non-zero deviceId, the fountain is already bound to an
app account, and an all-zero secret will be rejected.

**How to obtain your own secret: [docs/secret.md](secret.md).**

## Command reference

Commands this project sends, all read-only:

| Cmd | Meaning | Notes |
|---:|---|---|
| 213 | ping / deviceId + serial | works unauthenticated |
| 86 | verify secret | 8-byte forward-padded secret |
| 210 | state snapshot | 30-byte payload |
| 212 | pending-record counter | reply is `01 \| BE32 pending` |
| 80 | start history stream | see below |
| 230 | *(inbound)* state push | 42-byte payload, device-initiated |
| 68 | *(inbound)* history stream packet | `FA FC FE` header |

### Commands you must not send

| Cmd | Why not |
|---:|---|
| **73** | Permanently rewrites deviceId + secret. Can lock the official app out of your own fountain. **Only a physical factory reset undoes it.** |
| **67, 69** | Stream acknowledgements. They mark records as synced and the app can never display them again. |
| 220, 221, 222, 225, 226 | State-changing (power/mode, settings write, filter reset). Excluded here deliberately; they work, but this project is read-only by design. |

## Reading the drinking history

This is the part that is not documented elsewhere, and the part with the
interesting trick in it.

### Sequence

```
213  [00 00]                 ping / wake
86   <8-byte secret>         auth              -> 01
212  (empty)                 ask for pending   -> 01 | BE32 pending_bytes
80   <8-byte payload>        start the stream  -> 01, then CMD 68 packets
```

The `CMD 80` payload is `BE32(window) + BE32(mtu)`. The exact frame the app
sends, byte for byte:

```
fa fc fd 50 01 0b 08 00 00 00 00 20 00 00 00 9e fb
```

which is window = 32, mtu = 158. **`CMD 80` is what actually triggers the
stream**. `CMD 212` only reports how much is waiting.

### Streamed frames use a different header

Normal traffic is `FA FC FD` with a 7-byte header. History packets arrive as
**`FA FC FE` with a 9-byte header**:

```
FA FC FE | cmd tip seq | flag(1) len(LE16) | payload | FB
```

A parser written for the normal header drops the history silently and you
conclude the device sent nothing.

### Record format

Six bytes per record:

```
workTime  BE32   unix seconds, when the visit started
stayTime  BE16   duration in seconds
```

Verified live: `6a857feb 003d` → 2026-08-19 13:05:31, 61 seconds.

### The pending counter is at offset 1

The `CMD 212` reply payload is `status(1) | BE32 pending`. Reading the count
from offset 0 yields nonsense like 16777216. This mistake was made here.

### ⚠️ Never acknowledge, and why that is the useful part

The app follows a read with `CMD 67` and `CMD 69`, which tell the fountain the
records are synced. After that the counter drops to zero and **the app itself
can never show those records again.** Measured: 3 records pulled with acks, and
the second query returned a count of 0.

**If you never send the acks, nothing is consumed.** The records are returned in
full, the pending counter stays exactly where it was, and the phone app still
displays the history. Measured and confirmed on the device.

The consequence is that a third-party reader can run **alongside** the official
app instead of cannibalising it. The cost is that the fountain replays its whole
buffer on every poll, so the reader has to deduplicate on timestamp, a cheap
price. Any tool built on this protocol should read without acking.

A pleasant side effect: because the device keeps the buffer, a gateway restarted
at noon still reconstructs the whole morning. On 22 Aug 2026 a board that had
rebooted at 16:09 produced a complete report going back to 04:15, entirely from
the fountain's own buffer.

## State payload

`CMD 230` pushes 42 bytes unsolicited while connected; `CMD 210` returns the
first 30 on request.

```
[0]      power                    [1]      suspended
[2]      mode (1=continuous, 2=intermittent)
[3]      power source (2=adapter) [4]      do-not-disturb
[5:9]    fault / no-water / low-battery / filter warnings
[9:13]   pump total    BE32 seconds
[13]     filter %                 [14]     pump running
[15:19]  pump today    BE32 seconds
[19]     detect (0 = nothing, 2 = cat present; 1 never observed)
[20:22]  supply mV     BE16       [22:24]  battery mV BE16
[24]     battery %                [25]     module
[26:28]  proximity BASELINE  LE16
[28:30]  proximity RAW       LE16
[30]     smart-on minutes         [31]     smart-off minutes
[32:34]  battery runtime          [34:36]  battery sleep
[36]     LED                      [37]     brightness
[38]     always 0                 [39]     child lock
[40]     always 0                 [41]     always 1
```

**There is no drinking counter in here.** Five visits over six hours moved no
byte in a counter-like way. History is only available through the stream above.

### Proximity sensor (bytes 26-29)

Capacitive, 12-bit ADC, little-endian, with an **auto-calibrating baseline** that
drifts with temperature. It moved 1680 → 1715 over one night. So an absolute
threshold is wrong; compare against the reported baseline.

Measured over a full night: raw ≈ baseline + 5 with no cat; 2000-4095 with a cat.
Maximum with no cat **1981**, minimum with a cat **1996**, with no overlap. A
threshold of roughly baseline + 308 separated them cleanly, and `[19]` flips
0 → 2 at the same moment.

## Device behaviour worth knowing

**Records are written 1-2 minutes late.** The pending counter does not move the
instant a visit ends; the fountain writes the record about 40 seconds afterwards.
Poll immediately and you will conclude no record was created. Anything that
closes out a day must wait past midnight for this reason.

**The fountain merges nearby detections into one visit.** Reverse-engineered
from the app: detections 23 s apart become one visit, 48 s apart stay separate,
so the threshold is somewhere between (30 s works). Duration is *last release −
first capture*, the span, not the sum of the parts. Short weak touches are
discarded: the shortest visit the app counted was 33 s, the longest touch it
ignored was 9 s. Applying this rule reproduced all five of the app's visits for
a night, independently.

**Push rhythm.** While connected the fountain sends a burst of 4-5 state pushes
at the top of each minute, 3 s apart, on a fixed wall-clock phase, then goes
quiet for ~51 s. **But a detection edge triggers an immediate extra push**, both
when the cat arrives and when it leaves, off-grid. So presence detection is
effectively real-time.

**A missed edge is never repeated.** An event that happens while you are not
connected did not happen, as far as you are concerned. Detection accuracy is
therefore just your connected-time ratio.

**Connections are killed by the device after a fixed 28.7 s.** Reconnecting
immediately gave 83.6 % coverage over six hours (623 connections, mean reconnect
5.6 s). Acknowledging pushes does not extend the connection. Tried, no effect.

**Single connection slot, and it is worse than it sounds.** While the PetKit app
is connected, the fountain **stops advertising entirely**. Scanning does not see
it; connecting by address fails. This is indistinguishable from "unplugged" and
is very easily mistaken for a Bluetooth stack bug. It comes back within seconds
of the app closing.

For a polling gateway this is usually fine, since it holds the radio for a few seconds
every five minutes, but you cannot have the app open and expect the gateway to
work at the same time.
